## 1. 目标与公开边界

解决用户接听后确认是骚扰、但现有数据未识别的问题。用户可以提交“这是骚扰电话”，并管理当前安装实例提交的记录。现有的“查询结果准确／不准确”反馈仍是另一项功能。

本文件位于开源仓库，仅描述客户端行为、公开接口契约、兼容性和验证要求。公共标记的具体生效阈值、服务端表结构、风控参数与管理实现由服务端单独维护；不引用私有仓库地址、内部路径或运维资料。客户端使用的接口和身份机制不能被视为秘密。

## 2. 已确认的产品规则

1. 从 App 已有来电记录发起，不提供任意号码输入。所有识别结果类型都可以作为入口，不限于未命中号码。
2. 真正提交还必须持有该记录对应的有效官方 `feedback_token`。缺失、过期或已用于上报时不自动查询、不自动补领。
3. 只提交“骚扰”判断，不选择分类，不收集文字说明、通讯录、录音或完整通话记录。
4. 上报提交给官方，并携带当前安装的设备 ID。上报不自动加入本机黑名单。
5. 不登录、不强制设备完整性校验，不新增独立设备凭证、签名或注册流程。
6. 同一安装对同一号码最多贡献一张有效票；Token 更换不能重复计票。
7. 社区标记独立于现有 Provider 查询结论，首期仅通过官方在线查询提供，不加入离线库。
8. 默认只展示社区提示。用户可单独开启“拦截社区标记号码”，默认关闭。
9. 允许撤回，撤回停止本设备的贡献；已撤回历史长期保留，用户可以进一步删除对应服务端历史。
10. 查询、撤回、删除只使用设备 ID，不要求反馈 Token，Token 过期或本地来电记录被删除不影响这些操作。
11. 设置页与首页操作菜单均提供“我的上报”入口，共用一个二级页面，不新增底部导航项。
12. 设备身份仅限当前安装。卸载或清除数据后，不恢复原 ID，也不能再管理旧身份的记录；不跨设备迁移。

“所有记录可作为入口”不等于“所有记录都有提交资格”：本地命中、查询失败及自建响应通常没有官方 Token。用户曾明确发起的普通重查流程不在本次修改范围内；上报流程本身不会代替用户重查。

## 3. 设备身份与隐私

拟使用 `SecureRandom` 生成 32 字节随机值，以无 padding 的 base64url 编码作为 `device_id`。这里的“设备”实际表示安装实例，不采集 IMEI、序列号、ANDROID_ID 或其他硬件标识，不宣称能识别独立真人。

- 首次用户主动使用上报／管理功能时按需生成，并原子持久化；并发调用必须取得同一个 ID。
- 使用专门的 `ReportDeviceIdentityStore`，文件位于 `Context.noBackupFilesDir`，不放入会被系统备份的普通配置文件。
- 不进入 Auto Backup、设备迁移、App 手工备份、SavedState、剪贴板、日志、崩溃附加信息或分析事件。
- ID 无法读取时不能静默覆盖并伪装成空列表。提示身份不可用；用户明确选择建立新身份后才生成新的 ID，并告知旧记录无法管理。
- 首期不提供 ID 展示、导出、复制或恢复入口。

仅凭 `device_id` 即可查询和修改其记录，因此它事实上是访问凭据。使用 HTTPS、随机性和日志隔离减少暴露，但不能防止已获得 ID 的人访问记录，也不能防止恶意客户端批量生成 ID。此风险是已选择方案的限制，不以“无登录”或“服务端不开源”掩盖。

## 4. 客户端交互与状态

### 4.1 来电记录中的上报

详情显示“上报骚扰”入口；没有官方 Token 时说明不可用原因，不导航到官方查询或触发后台联网补领。已提交质量反馈不能直接被判为“不能上报”，两种消费状态独立。

提交确认文案至少说明：向官方提交该号码及当前安装标识、仅表示用户认为是骚扰、不自动加入个人黑名单。即使当前查询 Backend 已切为自建，使用历史官方 Token 的上报仍需清晰注明接收方是官方。

状态为 `Idle → Submitting → Accepted / Failure`。只在服务端确认后显示成功；按钮防重复点击。网络中断可能发生在服务端提交成功之后，此时允许通过“我的上报”核实，不把请求失败等同于服务端未保存。

Token 是不透明值。客户端不自行解码来判断认证有效性。新增响应中的到期时间只能用于提示，服务端判定始终权威；旧记录没有到期时间时允许提交校验，返回过期后禁用该 Token 的上报。

### 4.2 我的上报

- 设置入口与首页菜单共用 `MyReportsScreen` 和 `MyReportsViewModel`，沿用现有二级页面导航方式。
- 从官方服务分页获取全部有效及已撤回记录，按上报时间倒序；不以本地 `BlockedCall` 为列表数据源。
- 每行显示号码、上报时间、“有效／已撤回”、撤回时间（若有），以及独立的社区标记状态。
- 区分“我的上报有效”和“号码已经形成社区标记”；不能把单次上报成功展示成公共标记生效。
- 提供加载、空、失败、重试、刷新与加载更多状态；刷新失败不把旧列表错误清空。
- 页面不显示反馈 Token 或设备 ID；不展示其他设备的记录。
- 首期列表采用内存缓存，退出进程后重新获取，不新增持久化云端列表副本。

### 4.3 撤回、删除与重新上报

| 当前状态 | 可用操作 | 成功结果 |
| --- | --- | --- |
| 有效上报 | 撤回 | 移除本设备贡献，转为已撤回，保留历史 |
| 已撤回 | 删除历史 | 删除对应服务端历史，列表移除，不再次扣票 |
| 已撤回 | 不提供无凭据“恢复” | 要再次上报，回到已有来电记录并提供可用 Token |

两种破坏性操作均明确说明效果并二次确认。失败不提前移除行；成功后刷新对应记录及列表。重复撤回、重复删除应安全重试。删除本地来电记录、清空通话历史不调用云端撤回或删除。

重新上报形成新的上报生命周期，旧的已撤回历史保留直至用户删除；同一号码仍最多存在本设备一张有效票。

## 5. 拟议公开接口契约（版本 CR-1）

所有接口均使用固定官方 HTTPS Client，不复用自建 Token、Pin、URL 或 Client。管理请求不读取活动 Backend 来决定目标地址。

设备 ID 与 Token 只放 JSON 请求体，不放 URL、查询参数或游标。请求体不进入访问日志或网络调试日志。所有响应禁止公共缓存，游标不是认证凭据。

### 5.1 上报管理

| 方法与路径 | 请求字段 | 成功响应 |
| --- | --- | --- |
| `POST /api/v2/community/reports` | `device_id`, `feedback_token` | `report`, `created` |
| `POST /api/v2/community/reports/list` | `device_id`, `cursor?`, `limit?` | `items`, `next_cursor` |
| `POST /api/v2/community/reports/withdraw` | `device_id`, `report_id` | `report` |
| `POST /api/v2/community/reports/delete` | `device_id`, `report_id` | `status: "deleted"` |

创建时不另传可替换的号码，服务端以已认证 Token 对应的号码原字符串为准，不在上报阶段再次合并格式、国家码或前缀。App 在取得官方查询结果时保存对应 `response.phone` 为 `feedbackPhone`，上报响应用该快照核对，不直接对比系统来电原始号码。旧记录无快照时仅用原查询入口的 `PhoneNumberNormalizer.normalizeForLookup()` 推导核对值，不解码 Token、不补查；不匹配时提示结果待核实并引导查看列表，不能声称服务端未提交。

列表按 `report_id` 去重，不按客户端号码归一化合并云端记录；撤回／删除使用原 `report_id`。`report_id` 全程按字符串处理，不转整数进行排序或计算。

`report` 字段：

- `report_id`、`phone`、`reported_at`；时间为 RFC3339 UTC。
- `status`：`active` 或 `withdrawn`；未知值保守展示且禁用状态依赖操作。
- `withdrawn_at`：可空。
- `community_status`：`active`、`inactive` 或 `unavailable`，代表获取时的社区状态，不代表历史通话发生时的状态。

列表缺省每页 20 条，上限 100；`next_cursor` 为 null 表示末页。游标排序基于不可变的上报时间和 ID，刷新从第一页开始；客户端按 `report_id` 合并去重。

同设备、同号码已有有效上报时返回该上报且 `created=false`，不产生新票；已消费 Token 对同一上报的安全重试也不能复活已撤回或已删除记录。提交结果不确定时以列表核实为准。

错误体使用 `code` 和用于诊断的通用 `error`；UI 仅本地化已知 code，不直接展示服务端原文。

| HTTP / code | App 行为 |
| --- | --- |
| 400 `INVALID_REQUEST` / `INVALID_FEEDBACK_TOKEN` | 提示参数／凭据不可用，不自动补领 |
| 410 `FEEDBACK_TOKEN_EXPIRED` | 提示过期，不影响列表、撤回或删除 |
| 409 `REPORT_TOKEN_ALREADY_USED` | 提示已使用，可查看列表；不更改质量反馈状态 |
| 409 `REPORT_NOT_WITHDRAWN` | 提示先撤回，刷新记录 |
| 404 `REPORT_NOT_FOUND` | 刷新，不推断其他设备是否存在该记录 |
| 429 `RATE_LIMITED` | 遵循 `Retry-After`，不密集重试 |
| 503 `COMMUNITY_UNAVAILABLE` | 功能暂不可用，保留已加载内容 |
| 500 `INTERNAL_ERROR` / 传输失败 | 可重试或查列表核实，不宣称提交失败一定未落库 |

旧服务不支持路径时可能返回无业务 code 的 404，显示“服务暂不支持”，不能当作空列表。删除不存在或不属于当前设备的记录统一返回 `deleted`，避免泄露归属；服务端不能因此删除他人的记录。

限流冷却按操作维护，遵循合法 `Retry-After`；不自动重试写操作，也不把上报限流或禁用当作整个管理模块永久不可用。某次提交返回 503 后仍允许用户主动尝试查询、撤回、删除；服务端独立停用查询增强时，不改变原 Provider 结果。

请求严格按契约序列化，不添加 `phone`、设备名称或调试字段；省略游标时不发送空字符串，页大小固定 20。官方管理请求使用官方网络栈派生的专用配置，关闭重定向及自动连接重试、设置有界 call timeout，避免设备 ID 或 Token 被 307/308 转发至其他目标，不更改来电查询 Client 的现有超时。

### 5.2 官方查询响应扩展

`POST /api/v2/query` 拟增加以下可选字段，不修改原有 `is_spam`、`tag`、`source` 等字段的 Provider 语义：

- `community: { status: "active" | "inactive" | "unavailable" }`
- `feedback_token_expires_at: RFC3339 UTC | null`

旧响应缺失 `community` 按未提供社区结果处理，不据此拦截；缺失到期时间不自行推断 Token 已过期。自建响应不获得官方社区结果的可信身份，客户端在 Backend 边界丢弃自建返回的官方社区扩展及反馈 Token。

社区信息是可选增强，不能把该字段解析异常升级为整次原有查询失败；未知状态按 `unavailable` 处理。首期不在上游查询失败时单独发起社区查询，也不改变现有失败放行规则。

## 6. 来电决策、展示与缓存

- 保留通讯录、号码黑白名单、国际号码门禁、本地优先和现有标签规则的优先级；不为取得社区数据绕过这些边界。
- 原 Provider／本地决策本来要拦截的号码仍按原规则处理。社区“只提示”不能反向放行已有拦截结论。
- 原规则未要求拦截且官方结果有社区标记时，默认仅提示；开启社区拦截后才可作为新增拦截原因，仍尊重“仅提示不拦截”等全局模式，不设置 `forceBlock`。
- 社区状态单独建模，不伪装为 Provider 的 `tag` 或手写本地标签；不参与既有标签黑白名单匹配。
- 保留机构资料或原有识别名称，社区提示作为补充展示，避免覆盖身份资料。
- `CheckResult`、历史记录、手动重试、Overlay 与 Directory 展示需要贯通独立社区状态。历史记录保留当时的决策快照，撤回不追溯修改已完成的来电处置。
- 新增“拦截社区标记号码”设置，默认 false；切换后不得沿用旧的已计算拦截决定，优先从复用的原始响应按当前设置计算。

服务端对后续实际查询返回最新社区状态；客户端不承诺跨设备即时推送。现有来电查询复用最多 60 秒，社区状态不得在这一窗口之外继续作为新来电拦截依据；历史持久化记录不得变成长期社区拦截缓存。当前设备撤回成功后清除对应的查询复用及 Provider 展示缓存；撤回期间开始的旧请求通过代次校验防止回灌。其他设备的撤回最多受当前查询复用窗口影响。无有效新结果时不能用过期社区状态拦截。

## 7. App 分层与改动范围

以下为职责设计，不要求机械按文件数量拆分：

- `data/remote/`：独立 `OfficialCommunityReportApi` 及 DTO，复用现有官方网络栈的连接与 TLS 边界，不复用原反馈提交接口。
- `data/repository/CommunityReportRepository`：上报、列表、撤回、删除及错误映射；服务端为状态事实来源。
- `data/ReportDeviceIdentityStore`：安装 ID 的原子生成、读取与不可备份存储。
- `viewmodel/MyReportsViewModel`：分页、刷新、逐项请求状态；来电详情的上报协调继续遵循现有 ViewModel 职责。
- `ui/screen/MyReportsScreen`、`HomeScreen`、`SettingsScreen`、`MainActivity`：两个入口、共用页面、确认交互。
- `QueryRepository`、`QueryBackend`、`SpamNumberRepository`、`CheckResult`、来电 Service、Provider 及 Overlay：可信社区结果传递和保守决策。
- `AppDatabase` / `BlockedCall`：新增独立社区决策快照、`feedbackPhone`、Token 到期提示和独立上报用途状态，使用下一未占用版本迁移；旧记录社区状态缺省未知。Token 与绑定快照同批更新；网络重查不追溯覆盖来电发生时的社区处置快照。
- 不把原 `feedbackStatus` 当作社区上报状态；质量反馈成功、过期等本地状态不能替代独立的上报消费结果。旧请求完成时仅按期望 Backend／Token 条件更新相关字段，不能整行覆盖后来取得的新 Token 或用户备注。
- 系统自动备份及设备迁移排除运行时 `app-database` 和相关 journal/WAL/SHM 文件，保留现有自建凭据排除；不关闭整个应用的系统备份，不影响其他已有配置。UI 说明通话记录、名单和本地标签应使用 App 手动备份迁移；不能承诺删除此前系统已经保存的旧备份。
- 手动备份纳入社区状态与实际社区拦截原因的历史快照，升级格式并兼容旧版本；只作历史展示，恢复后不获得上报资格或实时拦截依据。设备 ID、Token、`feedbackPhone`、到期凭据元数据及设备上报管理状态仍排除。
- 所有新增权限、第三方 SDK 均不在本方案范围内。

## 8. 发布与验证

先部署支持 CR-1 的服务端，再发布 App。公开客户端不硬编码公共标记生效阈值，不展示未经接口提供的票数。旧 App 忽略新增字段且不会因社区结果被改变原有 Provider 结论；新 App 对旧服务优雅降级。

按项目规则，实施阶段执行 `:app:assembleDebug`、受影响的 lint 与设备场景验证；默认不新增或运行单元测试。本次已完成客户端实现和静态验证；具体命令结果及未执行的设备／服务端场景见实施计划末尾。

验收场景：

1. 同一有效官方 Token 分别提交质量反馈和社区上报，互不影响；过期 Token 不能新上报，但管理功能可用。
2. 无 Token、本地命中、自建 Token 不触发官方补查，不误报成功；持有历史官方 Token 的显式操作仍走官方。
3. 多次点击、超时重试、同号码不同来电记录不重复计票；提交响应丢失后能通过列表核实。
4. 撤回保留历史，删除历史不再扣票；列表刷新能处理另一会话或官方操作带来的状态变化。
5. 删除本地来电记录不删除云端上报；两个管理入口一致；退出进程后能重新获取列表。
6. 卸载／清数据及系统迁移使用经授权的可丢弃环境确认 ID 和运行时数据库不恢复；旧身份数据不会出现在新安装。手动备份兼容旧版本，恢复新格式只还原社区历史展示，不还原凭据、上报资格或实时拦截缓存。
