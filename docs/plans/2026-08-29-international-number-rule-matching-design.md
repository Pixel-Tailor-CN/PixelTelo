# 国际号码自定义规则匹配回归修复设计

## 1. 背景

GitHub Issue [#10](https://github.com/Pixel-Tailor-CN/PixelTelo/issues/10) 报告：用户在中国大陆之外使用本地自定义黑名单时，已有国际号码前缀规则无法继续命中真实来电。典型场景如下：

- 黑名单前缀规则：`+1519`；
- 来电号码：`+15197292346`；
- “不联网查询”开启；
- “仅提示不拦截”关闭；
- 无可用网络；
- 预期：命中本地黑名单并拦截；
- 实际：本地规则未命中，Test Intercept 又强制联网，最终显示联网失败结果并放行。

当前 `PhoneNumberNormalizer.normalizeCountryCode()` 只在完整北美号码长度为 12 时移除 `+`：

```text
+15197292346 -> 15197292346
+1519        -> +1519
```

因此来电号码与前缀规则进入了不同的格式域。该问题不仅影响 Test Intercept，也影响真实来电的本地黑白名单匹配。

此外，`SettingViewModel.testBlock()` 当前使用 `forceNetworkQuery = true`。本地规则未命中后，该参数会绕过“不联网查询”设置，使测试结果与真实来电配置不一致。

## 2. 目标

本设计需要实现以下目标：

1. 国际号码可继续使用本地自定义黑名单和白名单。
2. `+国家代码` 与 `00国家代码` 两种明确国际格式视为等价。
3. 不带 `+` 或 `00` 标记的纯数字号码不与明确国际格式等价。
4. 已保存的 `+1...` 与 `001...` 精确或前缀规则无需迁移即可继续工作。
5. 明确的非中国国际号码不查询国内离线数据库，也不发送到官方或 Self-hosted Backend。
6. Test Intercept 使用与真实来电相同的设置和查询边界。
7. 实际拦截、历史记录中的名单状态及规则管理 UI 使用同一匹配语义。
8. 不降低现有中国号码、和多号、标签规则、归属地规则及 `forceBlock` 行为的兼容性。

## 3. 非目标

本期不包含：

- 根据纯数字号码的长度或号段推断国家；
- 引入 libphonenumber 或其他第三方号码解析依赖；
- 增加用户地区或国际模式设置；
- 为号码规则增加国家、地区或号码类型字段；
- 修改官方查询接口协议；
- 将无国际标记的 `15197292346` 自动视为北美号码；
- 对标签规则、归属地规则或本地号码标签改变语义；
- 上传国际号码或自定义规则。

## 4. 产品规则

### 4.1 明确国际号码

号码清理空白、短横线与括号后，满足以下任一条件时，认定为“明确国际号码”：

- 以 `+` 开头，且不以 `+86` 开头；
- 以 `00` 开头，且不以 `0086` 开头。

示例：

| 输入 | 是否明确国际号码 |
| --- | --- |
| `+15197292346` | 是 |
| `0015197292346` | 是 |
| `+442071838750` | 是 |
| `00442071838750` | 是 |
| `+8613800138000` | 否 |
| `008613800138000` | 否 |
| `13800138000` | 否 |
| `15197292346` | 否 |

本设计采用保守判定：无 `+`/`00` 国际标记时，不推断其所属国家。

### 4.2 等价关系

本地自定义号码规则使用以下等价关系：

```text
+15197292346 == 0015197292346
+15197292346 != 15197292346
0015197292346 != 15197292346
```

中国号码继续保持现有国内等价关系：

```text
+8613800138000 == 008613800138000 == 13800138000
```

### 4.3 精确与前缀规则

上述等价关系同时适用于精确规则和前缀规则：

| 规则 | 来电 | 结果 |
| --- | --- | --- |
| `+1519*` | `+15197292346` | 命中 |
| `+1519*` | `0015197292346` | 命中 |
| `001519*` | `+15197292346` | 命中 |
| `1519*` | `+15197292346` | 不命中 |
| `1519*` | `0015197292346` | 不命中 |
| `1519*` | `15197292346` | 命中 |

无国际标记的规则和来电保持纯数字域，不跨域匹配明确国际号码。

## 5. 总体方案

采用“有限匹配候选集”方案，不修改 Room schema，也不批量改写已有规则。

设计分为两个独立的号码处理域：

1. **自定义规则域**：服务于本地黑白名单，保留明确国际语义，并兼容 `+`/`00` 两种写法。
2. **国内识别域**：服务于 MastDatabase、官方接口和 Self-hosted Backend，继续使用现有国内标准化逻辑；明确国际号码不得进入该域。

两个域不得再共享一个会丢失国际标记的单一字符串作为全部用途的号码键。

## 6. 自定义规则匹配器

### 6.1 组件职责

在数据层新增纯 Kotlin 组件
`app/src/main/java/vip/mystery0/pixel/telo/data/PhoneNumberRuleMatcher.kt`。它只负责号码规则语义，不访问数据库或 Android API。

固定接口：

```kotlin
object PhoneNumberRuleMatcher {
    fun normalizeRuleForStorage(value: String): String
    fun matchCandidates(phoneNumber: String): List<String>
    fun ruleMatches(rule: String, isPrefix: Boolean, phoneNumber: String): Boolean
    fun isExplicitInternational(phoneNumber: String): Boolean
}
```

`normalizeRuleForStorage()` 用于新增号码规则；`matchCandidates()` 用于 DAO 有界候选查询；
`ruleMatches()` 用于 UI 当前名单状态；`isExplicitInternational()` 用于国内数据库与实时查询门禁。
UI 与 Repository 不得复制匹配算法。

### 6.2 通用格式清理

匹配器首先执行与现有号码标准化一致的安全清理：

- `trim()`；
- 删除空白字符；
- 删除 `-`、`(`、`)`；
- 不删除 `+`；
- 不把其他字符静默解释为数字。

### 6.3 新规则存储格式

新增号码规则时：

- 明确国际 `00...` 统一保存为 `+...`；
- 明确国际 `+...` 保持 `+...`；
- `+86...` 与 `0086...` 保存为国内号码；
- 无国际标记的纯数字号码保持纯数字；
- 已确认的和多号前缀继续按现有规则处理；
- 标签规则与归属地规则只执行现有 `trim()`，不进入号码匹配器。

示例：

| 输入规则 | 新保存值 |
| --- | --- |
| `001519` | `+1519` |
| `+1519` | `+1519` |
| `1519` | `1519` |
| `+86138` | `138` |
| `0086138` | `138` |

### 6.4 来电匹配候选

为单次来电生成有序、去重、数量有界的候选集。

明确国际号码：

```text
输入 +15197292346
候选：+15197292346, 0015197292346

输入 0015197292346
候选：+15197292346, 0015197292346
```

无国际标记号码：

```text
输入 15197292346
候选：15197292346
```

中国号码继续生成国内规范值以及现有升级兼容候选；和多号场景继续保留去除已确认前缀后的号码，并在必要时回退旧格式规则。

候选集严禁为明确国际号码生成无 `+`/`00` 的纯数字候选，否则会违反已确认的产品语义。候选顺序固定以 `+` 规范形式优先、`00` 兼容形式其次，使同时存在两种旧规则时的跨格式选择保持稳定。

### 6.5 已有规则兼容

不迁移 `user_list` 数据。匹配时针对每个来电候选调用现有 DAO 查询：

```kotlin
candidates.firstNotNullOfOrNull { candidate ->
    dao.findMatch(candidate, listType)
}
```

现有 DAO 使用 `SUBSTR` 进行前缀匹配，因此：

- 已有 `+1519` 规则会命中 `+...` 候选；
- 已有 `001519` 规则会命中 `00...` 候选；
- 已有 `1519` 规则不会命中明确国际候选；
- 查询次数只随小型候选集增加，不读取完整名单。

黑名单和白名单必须使用完全相同的候选逻辑。

## 7. UI 名单状态一致性

`HomeViewModel` 当前有独立的 `UserListEntry.matchesPhone()` 实现。该实现必须删除重复的号码标准化逻辑，改为调用共享匹配器。

以下消费者必须使用同一语义：

- `UserListRepository.findBlackListMatch()`；
- `UserListRepository.findWhiteListMatch()`；
- 历史记录的 `CurrentListState`；
- 快速添加前的当前名单判断；
- 规则管理页中与号码匹配有关的状态。

目标是保证：实际来电是否命中与 UI 显示是否在名单中永远一致。

## 8. 国内数据库与实时查询边界

`SpamNumberRepository.checkSpam()` 的执行顺序调整为：

1. 使用自定义规则匹配器检查白名单；
2. 使用自定义规则匹配器检查黑名单；
3. 判断来电是否为明确国际号码；
4. 若是明确国际号码且未命中自定义规则，直接 Fail Open；
5. 仅非明确国际号码继续查询 MastDatabase；
6. 按“不联网查询”设置决定是否访问远端；
7. 允许联网时才调用当前 Backend。

明确国际号码未命中自定义规则时返回：

```kotlin
CheckResult(
    shouldBlock = false,
    label = "",
    resultType = ResultType.PASS_BUT_NOTIFY,
    localCost = ...,
    networkCost = 0,
    locationLookupAttempted = false,
)
```

约束：

- 不打开 MastDatabase；
- 不获取 Backend Snapshot；
- 不调用官方或自建实时查询；
- 不产生联网失败历史记录；
- 不显示归属地 Overlay；
- `forceNetworkQuery` 不能绕过国际号码查询边界。

该边界只限制国内数据库与查询服务，不限制本地自定义规则。

## 9. Test Intercept 行为

`SettingViewModel.testBlock()` 不再传递 `forceNetworkQuery = true`，而是调用与真实来电相同的入口：

```kotlin
spamNumberRepository.checkSpam(testPhoneNumber)
```

预期行为：

- 本地黑名单命中：显示 `shouldBlock=true` 与 `BLACK_LIST`；
- 本地白名单命中：显示 `shouldBlock=false` 与 `WHITE_LIST`；
- 开启“不联网查询”且本地未命中：显示普通放行结果，不发起网络请求；
- 明确国际号码本地未命中：直接放行，不访问国内数据库或查询服务；
- 国内号码且允许联网：保持现有完整查询流程。

Test Intercept 不再提供隐式的“强制在线测试”语义。如未来需要单独测试 Backend，应通过查询服务设置中的专用测试入口完成，不复用拦截决策测试。

## 10. 数据与备份兼容性

本设计不修改 `UserListEntry` 字段，因此：

- Room 数据库版本不变；
- 不新增 migration；
- 备份格式版本不变；
- 已有备份中的 `+...`、`00...` 和纯数字规则保持原值恢复；
- 恢复后由运行时匹配器提供兼容；
- 新建规则会使用新的规范存储形式；
- 若数据库同时存在语义等价的 `+1519` 与 `001519` 旧规则，两条规则均保留，不在本期自动合并或删除。

当多条等价规则均可命中时，继续沿用 DAO 现有返回顺序；本期不改变规则优先级。产品上应避免依赖等价重复规则具有不同备注或 `forceBlock` 的确定优先级。

## 11. 性能约束

来电本地规则查询仍位于关键路径，必须保持轻量：

- 候选集必须有固定小上限；
- 不得读取全部号码规则后在内存扫描；
- 不新增网络或 ContentProvider 调用；
- 单个候选继续使用现有 DAO 精确/`SUBSTR` 查询；
- 标签与归属地规则不增加额外查询；
- 明确国际号码在自定义规则未命中后提前返回，可避免 MastDatabase 和网络开销。

本地规则及离线查询仍受现有来电性能日志和硬性时间约束约束。

## 12. 隐私与日志

- 不记录完整来电号码或规则正文；
- 国际号码提前返回只记录稳定英文分类，例如 `Explicit international number skipped`；
- 不把国际号码发送到官方或 Self-hosted Backend；
- 不在异常消息中包含号码、URL、Token 或响应正文；
- Test Intercept 的用户可见结果只展示既有输入与稳定结果类型。

## 13. 失败处理

- 自定义规则查询异常：沿用来电 Fail Open，不继续把国际号码发送到任何实时查询 Backend 作为补偿；
- 明确国际号码未命中：正常放行，不视为错误；
- 国内号码：继续使用现有联网失败分类；
- Test Intercept：使用稳定本地化错误提示，不直接展示异常正文；
- 候选生成结果为空：视为未命中并 Fail Open。

### 15.3 中国号码回归

验证：

- `+8613800138000`、`008613800138000`、`13800138000` 使用相同国内规则；
- `12583113800138000` 等已确认和多号前缀行为不回归；
- 国内 MastDatabase 查询和官方查询正常；
- 标签、归属地和 `forceBlock` 规则不受影响。

### 15.4 查询边界

为明确国际号码配置以下场景：

1. 本地黑名单命中：必须拦截，网络调用计数为 0；
2. 本地白名单命中：必须放行，网络调用计数为 0；
3. 本地未命中且“不联网查询”关闭：仍不得访问 MastDatabase、官方接口或 Self-hosted Backend；
4. 本地未命中且“不联网查询”开启：结果与场景 3 一致；
5. `forceNetworkQuery` 调试路径：仍不得绕过国际号码边界。

证据应来自稳定日志分类、Backend 请求计数或可控测试服务，不以“未看到 UI”代替网络未发生的证明。

### 15.5 Test Intercept 与真实来电

对同一国际号码和同一规则分别执行：

- Settings 中 Test Intercept；
- `adb emu gsm call` 真实 CallScreening 路径。

两者的 `shouldBlock`、`ResultType` 和规则命中必须一致。测试结束后取消模拟来电并删除临时规则。

### 15.6 备份恢复

- 备份并恢复已有 `+1519` 规则，恢复后继续匹配 `+`/`00` 国际号码；
- 备份并恢复已有 `001519` 规则，恢复后继续匹配；
- 纯数字 `1519` 规则恢复后仍不匹配明确国际号码；
- 不改变备份版本和其他范围的恢复计数。

## 16. 验收标准

以下条件全部满足时，Issue #10 可视为修复：

1. 已有 `+1...` 和 `001...` 本地规则无需重建即可命中对应明确国际来电。
2. `+...` 与 `00...` 等价，纯数字格式与它们不等价。
3. 黑名单、白名单、精确规则和前缀规则语义一致。
4. 历史记录当前名单状态与实际来电命中一致。
5. 明确国际号码不会访问国内离线库、官方接口或自建实时查询。
6. Test Intercept 遵循“不联网查询”等真实设置，不再强制联网。
7. Test Intercept 与真实来电对同一输入给出相同决策。
8. 中国号码、和多号及现有拦截策略无回归。
9. Room、备份格式、权限和依赖均无变更。
10. 编译、Lint、模拟器矩阵与清理检查通过。
